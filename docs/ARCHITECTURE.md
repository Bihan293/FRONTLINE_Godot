# FRONTLINE — архитектура и правила кода

Документ обязателен для новых фич и рефакторинга. Если правило нарушается,
это должно быть осознанным исключением, а не привычкой.

## 1. Владение состоянием

| Состояние | Где живёт | Кто читает | Кто пишет |
|---|---|---|---|
| Настройки игрока | `GameSettings` (autoload) | все системы | экран настроек |
| Конфигурация матча | `MatchState` (autoload) | сцены, игрок, боты | меню, экран деплоя |
| Здоровье, патроны, стойка | сам `player` | HUD, оружие | игрок и урон |
| Состояние конкретного бота | `soldier_bot` | его компоненты | его ИИ |
| Данные оружия | `FRONTLINEWeaponCatalog` | игрок, боты, тесты | только каталог |

**Запрещено** хранить игровое состояние в `get_tree().get_meta("selected_*")`
или в `Node.set_meta` на UI-нодах. Для поиска UI-элементов используем типизированные
поля скрипта, а не строковые ключи.

## 2. Типы вместо словарей

- Данные конфигурации оформляются как `Resource`/`RefCounted` с типизированными
  полями (`FRONTLINEWeaponDef`), а не `Dictionary` с ключами-строками.
- Публичные API имеют типы аргументов и возвращаемых значений.
- Массивы — типизированные: `Array[FRONTLINEWeaponDef]`, `Array[RID]`.
- Строковые `get("field")`/`call("method")` допустимы только на границе
  с GDScript-динамикой (урон по `Area3D`, тестовые хуки), не внутри своей системы.

## 3. Размер и ответственность файлов

| Тип файла | Ориентир |
|---|---:|
| Компонент/система | до 400–600 строк |
| UI-экран | до 500 строк |
| Фабрика контента (меши, layout) | без жёсткого лимита, но только данные/построение |
| Функция | до 60–80 строк; больше — разбить |

`player.gd` (~960 строк), `soldier_bot.gd` (~800) и `battlefield.gd` (~700) —
оставшийся технический долг. Новые фичи туда не добавляем без выделения компонента.

## 4. Направление зависимостей

```
core (MatchState, GameSettings, каталоги)
        ↓
systems (оружие, ИИ, навигация, транспорт)
        ↓
presentation (HUD, меню, эффекты, меши)
        ↓
scenes (.tscn)
```

- `core` не знает про сцены и HUD.
- Системы общаются сигналами, а не прямыми ссылками на UI.
- Сцена собирает компоненты, а не содержит логику.

## 5. UI

- Новые экраны делаем `.tscn` + скрипт, а не «построю всё в `_ready`».
- HUD обновляется по событиям, а не каждый кадр.
- Никаких `set_meta("map_details", node)` для доступа к элементам.

Все основные экраны — главное меню, деплой, HUD игрока, боевой HUD, пауза и
HUD-кастомайзер — живут в `scenes/*.tscn`. Их скрипты только связывают
события и заполняют динамические списки; новый UI не строится целиком в
`_ready`.

## 6. Тесты и приёмка

- Любая правка игровой логики проходит `tests/*_smoke`.
- Новый модуль получает хотя бы один headless-тест.
- CI собирает APK; красный CI = фича не готова.
- Для ИИ использовать `tools/ai_probe.tscn`, для производительности —
  `tools/perf_probe.tscn`, для визуала — `tools/screenshot_harness.tscn`.
